# URL 단축 서비스 학습 노트

URL 단축 서비스의 전체 구조와 병목 지점, 책에서 소개한 대응 방법을 정리한다.
이 문서는 학습 내용을 기록하는 노트이며, 프로젝트에서 확정한 설계는
[시스템 설계](design.md)와 [ADR](decisions/)에 별도로 기록한다.

## 핵심 문제: 중복되지 않는 단축 키를 효율적으로 생성하기

이 프로젝트의 단축 키는 Base62 문자로 구성된 7자리 문자열이다.
표현 가능한 키의 수는 `62^7 = 3,521,614,606,208`개이며, 정보량으로 환산하면
약 41.7비트다.

### 1. 무작위 생성

7자리 Base62 문자열을 무작위로 생성하고, 중복되지 않은 키가 나올 때까지
반복하는 방식이다. 저장소에는 다음과 같은 매핑을 저장한다.

```text
shortKey -> longURL
```

다음 문제를 처리해야 한다.

- 키가 이미 존재하는지 확인할 때마다 저장소 조회가 발생한다.
- 여러 서버가 동시에 같은 키를 생성하면 조회와 저장 사이에 경쟁 상태가 생긴다.

단순히 조회한 뒤 저장하면 경쟁 상태를 막을 수 없다. `putIfAbsent`나 데이터베이스의
unique constraint처럼 검사와 저장을 하나의 원자적 연산으로 처리해야 한다.
삽입에 실패하면 새로운 키를 생성해 다시 시도한다.

관련 최적화 방법은 다음과 같다.

- **KGS(Key Generation Service)**: 백그라운드 워커가 무작위 키를 미리 생성해
  미사용 키 저장소에 쌓아두고, 애플리케이션이 하나씩 가져간다.
- **Bloom filter**: 존재하지 않는 키를 빠르게 걸러 저장소 조회를 줄인다. 다만
  오탐(false positive)이 있으므로 중복 방지의 최종 수단으로 사용할 수는 없다.
- **의사난수 순열**: 숫자 ID에 Feistel network 등의 가역 변환을 적용해 순차적인
  값이 그대로 노출되는 것을 줄인다.
- **샤딩**: 키 공간이나 해시값을 기준으로 중복 검사와 저장 부하를 여러 파티션에
  분산한다.

### 2. MD5 해시

원본 URL의 MD5 해시를 이용해 단축 키를 만드는 방식이다. 같은 URL은 같은 해시를
만들기 때문에 중복 URL 처리에는 유리하지만, 128비트 MD5 전체를 7자리 Base62에
담을 수는 없다.

7자리 Base62 공간은 약 41.7비트이므로 해시를 해당 범위로 축소해야 한다.
42비트를 그대로 사용하면 일부 값은 `62^7`보다 크기 때문에, 나머지 연산이나
범위를 벗어난 값의 재처리 방법이 추가로 필요하다. 어떤 방법을 사용하더라도
출력 공간이 작아지는 만큼 서로 다른 URL이 같은 키를 만드는 충돌 가능성이 있다.

Birthday paradox에 따르면 약 3.5조 개의 키 공간에서도 약 220만 개의 키가
생성되면 충돌 확률이 약 50%에 도달한다. 따라서 해시 방식도 충돌 검사와 재시도
정책이 필요하다.

### 3. 중앙 카운터 방식

중앙 서버나 데이터베이스에서 숫자를 하나씩 증가시키고, 그 값을 Base62로
인코딩하는 방식이다. 카운터가 원자적으로 증가한다면 중복 검사가 필요 없다는
장점이 있다.

반면 모든 생성 요청이 중앙 카운터에 집중되므로 병목이 생길 수 있고, 복제와
장애 조치가 없다면 카운터가 단일 장애 지점(SPoF)이 된다.

타임스탬프, 호스트 ID, 밀리초 내 순번을 하나의 ID에 조합하는 방식도 있다.
예를 들어 호스트 ID에 6비트를 사용하면 최대 64개 호스트를 표현할 수 있고,
밀리초 내 순번에 4비트를 사용하면 한 호스트가 1밀리초에 최대 16개 ID를 만들 수
있다. 이 한도를 넘으면 다음 밀리초를 기다리거나 overflow 처리 정책이 필요하다.
이는 모든 카운터 방식의 고정된 한계가 아니라, 선택한 비트 배치에서 생기는
제약이다.

### 4. 분산 카운터 방식

중앙 카운터의 요청 집중을 줄이기 위한 후보 중 하나로 range/chunk 기반 할당이
있다. 범위 할당기가 각 서버나 데이터베이스 파티션에 서로 겹치지 않는 ID 범위를
나눠주고, 각 서버가 할당받은 범위 안에서 독립적으로 카운터를 증가시킨다.

검토해야 할 문제는 다음과 같다.

- 서버가 할당받은 범위를 모두 사용했을 때 새 범위를 안전하게 받아야 한다.
- 서버가 중간에 종료되면 사용하지 않은 ID 범위가 버려질 수 있다.
- 두 서버에 겹치는 범위를 할당하지 않도록 범위 할당 연산이 원자적이어야 한다.
- 범위 할당기 자체가 병목이나 단일 장애 지점이 되지 않도록 해야 한다.
- ID 사이의 빈 값을 허용할지, 사용하지 않은 범위를 회수할지 정책을 정해야 한다.

이 프로젝트는 무작위 생성, 중앙 카운터와 분산 카운터의 장단점을 비교한 뒤
range 기반 분산 카운터를 사용하기로 결정했다. 구체적인 선택과 장애 처리 정책은
[ADR 03. 분산 카운터로 단축 URL ID를 생성한다](decisions/03-use-distributed-counter-for-url-ids.md)에
기록한다.
